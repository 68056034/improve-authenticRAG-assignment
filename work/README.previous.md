# เปรียบเทียบระบบ RAG ก่อนและหลังปรับปรุง

เอกสารนี้อธิบายความแตกต่างระหว่างระบบ **(1) ก่อนปรับปรุง** และ **(2) หลังปรับปรุง** รวมถึงผลที่ดีขึ้น เหตุผล และข้อจำกัดที่พบจากการทดสอบด้วยคำถามภาษาไทยจำนวน 5 ข้อ

## 1. ระบบที่นำมาเปรียบเทียบ

| ระบบ | ไฟล์โปรแกรม | ไฟล์ผลลัพธ์ |
|---|---|---|
| **(1) ก่อนปรับปรุง** | `onlysearchAuthenticRAGbak.py` | `authentic_rag_search_resultsbak.json` |
| **(2) หลังปรับปรุง** | `onlysearchAuthenticRAG.py` | `authentic_rag_search_results.json` |

ทั้งสองระบบใช้ข้อมูลใน OpenSearch ชุดเดิม และตั้งค่าโมเดลสร้างคำตอบเป็น **Qwen2.5 7B ผ่าน Ollama** เหมือนกัน ดังนั้นการเปลี่ยนแปลงที่ต้องการศึกษาอยู่ในขั้นตอนการจัดอันดับเอกสารและการเตรียม context ก่อนสร้างคำตอบ

> การทดลองรอบนี้เปลี่ยนโมเดลของทั้งสองระบบจาก Qwen2.5 72B บน OpenRouter มาเป็น Qwen2.5 7B ในเครื่อง จึงเป็นการเปรียบเทียบก่อน–หลังภายใต้โมเดล 7B ไม่ใช่การเปรียบเทียบคุณภาพของ 72B กับ 7B ทั้งนี้ JSON ของระบบ (1) ไม่ได้บันทึกชื่อโมเดลไว้ การใช้โมเดลเดียวกันอ้างอิงจากการตั้งค่าในโค้ด

### 1.1 เหตุผลที่เปลี่ยนไปใช้ Local Model

เดิมระบบเรียก `qwen/qwen-2.5-72b-instruct` ผ่าน OpenRouter แต่ระหว่างทดสอบพบ error `402` เช่น `Prompt tokens limit exceeded: 9548 > 3793` พร้อม `limit_source: openrouter_credits` หมายถึงคำขอมีต้นทุนเกินเครดิตหรืองบที่รองรับได้ในขณะนั้น ไม่ใช่ว่า Qwen รองรับ prompt ได้สูงสุดเพียง 3,793 tokens ภายหลังพบว่ายอดเครดิตบัญชีติดลบ จึงเป็นข้อจำกัดที่การสร้าง API key ใหม่หรือรอรีเซ็ตวงเงินรายวันไม่ได้แก้ไข

อีกปัจจัยคือ context ภาษาไทยมีความยาวจริงมากกว่าที่โค้ดเดิมประมาณจากช่องว่าง ทำให้ระบบส่ง prompt หลายพัน tokens โดยไม่ถูกตัดตามงบที่ตั้งใจไว้ เมื่อเครดิตไม่เพียงพอจึงสร้างคำตอบไม่สำเร็จ [ข้อจำกัดเครดิตและงบคำขอของ OpenRouter](https://openrouter.ai/docs/api_reference/limits)

จึงเปลี่ยนทั้งระบบ (1) และ (2) มาใช้ **Qwen2.5 7B ผ่าน Ollama ในเครื่อง** โดยเรียก `http://127.0.0.1:11434/api/chat` การทำงานนี้ไม่ใช้เครดิต OpenRouter และสามารถทดสอบซ้ำได้โดยไม่เสียค่า API ตามจำนวน tokens รุ่น 7B ถูกเลือกให้เหมาะกับเครื่องที่มี RAM ประมาณ 16 GB และ RTX 3060 VRAM 12 GB มากกว่ารุ่น 72B ซึ่งไฟล์โมเดลบีบอัดบน Ollama มีขนาดประมาณ 47 GB ขณะที่รุ่น 7B ประมาณ 4.7 GB [Qwen2.5 72B](https://ollama.com/library/qwen2.5:72b), [Qwen2.5 7B](https://ollama.com/library/qwen2.5:7b)

การตั้งค่าที่ใช้เหมือนกันทั้งสองระบบคือ:

```python
"model": "qwen2.5:7b",
"options": {
    "num_ctx": 16384,    # context window ที่จัดสรรให้โมเดล
    "num_predict": 1000 # เพดาน tokens ของคำตอบ
}
```

> Local model ไม่ได้มี tokens ไม่จำกัด: ยังต้องให้ prompt และคำตอบอยู่ภายใน context window ที่ตั้งไว้ และใช้หน่วยความจำของเครื่อง ยิ่งเพิ่ม context ก็ยิ่งใช้หน่วยความจำมากขึ้น การย้ายไป local จึงแก้การพึ่งพาเครดิต OpenRouter แต่ไม่ได้แก้ความคลาดเคลื่อนของตัวนับ token หรือปัญหาคำตอบชนเพดาน output โดยอัตโนมัติ [Context length ของ Ollama](https://docs.ollama.com/context-length)

การเปลี่ยนจาก 72B เป็น 7B เป็นการเปลี่ยนโมเดลสร้างคำตอบด้วย แม้อยู่ในตระกูล Qwen2.5 เหมือนกัน ในรายงานนี้จึงถือเป็น **การเตรียมสภาพแวดล้อมใหม่สำหรับทั้งสองระบบ** แล้วเปรียบเทียบการปรับปรุง RAG ภายใต้โมเดล 7B ตัวเดียวกัน ไม่อ้างว่าความแตกต่างจาก 72B กับ 7B เป็นผลของ reranking ทั้งนี้ใช้เอกสารและ embedding เดิมใน OpenSearch ได้ โดยไม่ต้องนำเข้าข้อมูลใหม่เพียงเพราะเปลี่ยนโมเดลตอบคำถาม

## 2. ต่างกันตรงไหน

### 2.1 ระบบ (1): Hybrid Search และ RRF

ระบบเดิมค้นหาเอกสารด้วยสองวิธี:

1. **BM25:** ค้นหาจากคำที่ตรงกันในเนื้อหาและบริบทของเอกสาร
2. **Dense Search:** แปลงคำถามเป็น embedding ด้วย `BAAI/bge-m3` แล้วค้นหาเวกเตอร์ที่ใกล้เคียงใน OpenSearch

จากนั้นใช้ **Reciprocal Rank Fusion (RRF)** รวมอันดับของผลค้นหาทั้งสองวิธี และเลือก 5 chunks แรกเป็น context ให้โมเดลสร้างคำตอบ

เมื่อกำหนด `k=5` แต่ละวิธีจะค้นหา 10 chunks ก่อนรวมรายการ จึงมีผู้สมัครได้สูงสุด 20 chunks หากไม่มีเอกสารซ้ำกัน

RRF ใช้อันดับจากแต่ละระบบในการรวมผล ไม่ได้อ่านคำถามและเนื้อหาของแต่ละ chunk พร้อมกันเพื่อประเมินว่า chunk นั้นตอบคำถามได้โดยตรงหรือไม่

```text
คำถาม → BM25 + Dense Search → RRF → เลือก 5 chunks → สร้างคำตอบ
```

### 2.2 ระบบ (2): เพิ่ม Reranking หลัง RRF

ระบบที่ปรับปรุงใช้ขั้นตอนค้นหาเดิม แล้วเพิ่ม **Cross-Encoder Reranker** ด้วยโมเดล `BAAI/bge-reranker-v2-m3` หลังรวมรายการด้วย RRF

Reranker รับคู่ข้อมูล `(คำถาม, เนื้อหา chunk)` แล้วให้คะแนนความเกี่ยวข้องของแต่ละคู่ จากนั้นเรียงอันดับใหม่และเลือก 5 chunks ที่ได้คะแนนสูงที่สุดเป็น context

```text
คำถาม → BM25 + Dense Search → RRF
      → Reranker → เลือก 5 chunks → เตรียม context → สร้างคำตอบ
```

ข้อแตกต่างคือระบบ (2) ประเมินความสัมพันธ์ระหว่างคำถามกับข้อความโดยตรงเพิ่มเติมจากอันดับค้นหาเดิม จึงมีโอกาสเลื่อนเอกสารที่มีข้อมูลตอบคำถามขึ้นมา และลดอันดับเอกสารที่เพียงมีคำเกี่ยวข้องแต่ให้ข้อมูลไม่เพียงพอ

> คะแนน RRF และคะแนน reranker เป็นคนละชนิด จึงไม่สามารถนำตัวเลขมาเทียบตรง ๆ ได้ ตัวอย่างเช่น คะแนนที่เปลี่ยนจากประมาณ `0.016` เป็น `0.98` ไม่ได้หมายความว่าความแม่นยำเพิ่มขึ้นเป็น 98%

### 2.3 เพิ่มการจัดการ Context ภายใต้งบ Token

ระบบ (1) ประมาณจำนวน tokens ด้วยสูตร:

```python
estimated_tokens = len(context.split()) * 1.3
```

วิธีนี้อาจประเมินภาษาไทยต่ำกว่าความจริง เพราะข้อความภาษาไทยยาว ๆ อาจไม่มีช่องว่างแบ่งคำ เมื่อประมาณว่าข้อความยังไม่เกินเพดาน ระบบจึงส่ง context เต็มเข้าโมเดล

ระบบ (2) เพิ่มการนับด้วย tokenizer ของ Qwen และตั้งใจจำกัด prompt ทั้งชุด รวมคำถาม คำสั่ง และ context พร้อมสำรองพื้นที่สำหรับคำตอบ นอกจากนี้ยังบันทึก context ที่ส่งจริง จำนวน tokens จาก Ollama และเหตุผลที่โมเดลจบคำตอบ

| การตั้งค่า | ระบบ (1) | ระบบ (2) |
|---|---|---|
| การค้นหาเบื้องต้น | BM25 + Dense Search | BM25 + Dense Search |
| การรวมผล | RRF | RRF |
| การจัดอันดับเพิ่มเติม | ไม่มี | Cross-Encoder Reranker |
| จำนวน chunks ที่เลือก | 5 | 5 |
| การจำกัด context | ประมาณจากช่องว่าง | ตั้งใจนับด้วย tokenizer ของ Qwen |
| โมเดลสร้างคำตอบ | Qwen2.5 7B | Qwen2.5 7B |
| Context window ของ Ollama | 16,384 tokens | 16,384 tokens |
| เพดานคำตอบ | 1,000 tokens | 1,000 tokens |
| งบ prompt ที่ตั้งค่า | ไม่ได้จำกัด prompt ทั้งชุดด้วย tokenizer | 14,000 tokens และเผื่อ 256 tokens |
| ข้อมูล generation ใน JSON | ไม่ได้บันทึก | บันทึก usage, context และ finish reason |

**ข้อจำกัดที่พบ:** ตัวนับ prompt ในเครื่องของระบบ (2) รายงานเพียง `2` tokens ทุกคำถาม แต่ Ollama รายงานจริงประมาณ 5,800–6,600 tokens จึงยังยืนยันไม่ได้ว่าการจำกัด token ทำงานถูกต้อง การนับนี้ต้องได้รับการแก้ไขก่อนนำไปประเมินผลด้านการควบคุม context

### 2.4 โค้ดก่อนและหลังเพิ่ม Reranking พร้อมคำอธิบาย

ตัวอย่างต่อไปนี้คัดจากไฟล์ที่ใช้ทดลอง เป็นส่วนของคลาส `AuthenticSearchRAG` ไม่ใช่โปรแกรม standalone สำหรับคัดลอกไปรันทั้งไฟล์ สามารถดูโค้ดเต็มได้จาก [ระบบ (1)](onlysearchAuthenticRAGbak.py) และ [ระบบ (2)](onlysearchAuthenticRAG.py)

#### 2.4.1 ก่อนปรับ: เลือก Top-k จาก RRF ทันที

โค้ดจาก `onlysearchAuthenticRAGbak.py`:

```python
def hybrid_search(self, query, k=5, rrf_k=60):
    """ค้นหาแบบ hybrid ด้วย RRF ที่รวมผลจาก sparse และ dense search (เหมือนตัวอย่าง)"""
    # ค้นหาด้วย BM25 (sparse)
    sparse_results = self.sparse_search(query, k=k*2)
    print(f"\nSparse search found {len(sparse_results)} results")

    # ค้นหาด้วย vector similarity (dense)
    dense_results = self.dense_search(query, k=k*2)
    print(f"Dense search found {len(dense_results)} results")

    # ใช้ RRF ผสมผลลัพธ์
    rankings = [sparse_results, dense_results]
    fused_results = self.rrf_fusion(rankings, k=rrf_k)
    print(f"RRF fusion returned {len(fused_results)} results")

    return fused_results[:k]
```

อธิบายขั้นตอน:

1. `self.sparse_search(query, k=k*2)` ค้นหาเอกสารด้วย BM25 จำนวน `k*2` ชิ้น
2. `self.dense_search(query, k=k*2)` ค้นหาด้วย embedding จำนวนเท่ากัน
3. `self.rrf_fusion(rankings, k=rrf_k)` รวมอันดับผลค้นหาสองรายการ โดย chunks ที่มี `doc_id` เดียวกันจะถูกรวมคะแนน
4. `return fused_results[:k]` ตัดเหลือ `k` อันดับแรกตาม RRF แล้วส่งต่อไปสร้าง context ทันที

เมื่อ `k=5` จะค้นหา 10 ชิ้นต่อวิธี รวมได้สูงสุด 20 ชิ้นที่ไม่ซ้ำกัน แล้วเลือก 5 ชิ้นแรก โดยไม่มีการประเมินคู่คำถาม–ข้อความเพิ่มเติม

#### 2.4.2 โค้ด RRF ที่ทั้งสองระบบใช้เหมือนกัน

```python
def rrf_fusion(self, rankings, k=60):
    """ผสมผลลัพธ์การค้นหาด้วย Reciprocal Rank Fusion (เหมือนในตัวอย่าง)"""
    fused_scores = {}
    doc_sources = {}

    for ranker_id, results in enumerate(rankings):
        for rank, (doc_id, score, source) in enumerate(results):
            if doc_id not in fused_scores:
                fused_scores[doc_id] = 0
                doc_sources[doc_id] = source

            # RRF formula: 1 / (k + rank)
            fused_scores[doc_id] += 1.0 / (k + rank)

    # เรียงลำดับตาม RRF score
    sorted_results = sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
    return [(doc_id, score, doc_sources[doc_id]) for doc_id, score in sorted_results]
```

แต่ละผลค้นหาเป็น tuple `(doc_id, score, source)` โดย `source` มีเนื้อหา chunk และข้อมูลที่ดึงจาก OpenSearch ฟังก์ชันนี้ใช้ `rank` คำนวณคะแนนแทนการรวมค่า `score` ของ BM25 กับ vector search โดยตรง เนื่องจากคะแนนของสองระบบมีสเกลต่างกัน

ในโค้ดปัจจุบัน `enumerate(results)` เริ่มอันดับที่ **0** และใช้ `1 / (k + rank)` ดังนั้นอันดับแรกจากหนึ่งรายการมีส่วนร่วม `1 / 60 ≈ 0.01667` เมื่อ `k=60` หาก chunk ปรากฏในทั้งสองรายการ ก็จะได้รับส่วนร่วมจากทั้งสองรายการ

พารามิเตอร์ `k` ใน `rrf_fusion()` เป็นค่าคงที่ที่ใช้ในสูตร RRF ไม่ใช่จำนวนเอกสารที่จะคืน จึงส่ง `rrf_k` จาก `hybrid_search()` เข้ามา ส่วนจำนวนเอกสารสุดท้ายกำหนดด้วย `k` ของ `hybrid_search()`

> ตัวอย่างนี้รักษาวิธีนับอันดับเริ่มจาก 0 ของไฟล์จริงไว้ทั้งก่อนและหลัง เพื่ออธิบายระบบที่ใช้ทดลอง ไม่ได้เปลี่ยนไปใช้สูตรที่เริ่มอันดับจาก 1

#### 2.4.3 หลังปรับ: โหลดโมเดล Reranker หนึ่งครั้ง

ส่วน import และการตั้งค่าที่เพิ่มในระบบ (2):

```python
import os
import numpy as np
from sentence_transformers import SentenceTransformer, CrossEncoder

# ส่วนนี้อยู่ภายใน __init__ ของ AuthenticSearchRAG
self.use_reranker = os.environ.get("RAG_USE_RERANKER", "1") != "0"
self.reranker = (
    CrossEncoder("BAAI/bge-reranker-v2-m3", max_length=512)
    if self.use_reranker else None
)
```

- `CrossEncoder` เป็นโมเดลให้คะแนนคู่คำถาม–ข้อความ ไม่ใช่โมเดลสร้างคำตอบสุดท้าย
- โหลดใน `__init__` เพื่อใช้ซ้ำหลายคำถาม โดยไม่โหลดน้ำหนักใหม่ทุกครั้งที่ค้นหา
- `RAG_USE_RERANKER="1"` เปิด reranking ซึ่งเป็นค่าเริ่มต้น ส่วน `"0"` ปิดเพื่อทดลองผล RRF อย่างเดียวในไฟล์ระบบ (2)
- `max_length=512` จำกัดจำนวน tokens ของคู่ข้อมูลที่ reranker ประเมิน ข้อความยาวอาจถูกตัดเฉพาะตอนให้คะแนน **ไม่ได้ตัดเนื้อหาเต็มใน `source` ที่ส่งต่อไปเตรียมคำตอบ** จึงยังต้องจัดการ context แยกต่างหาก

#### 2.4.4 หลังปรับ: ให้คะแนนและเรียงผู้สมัครใหม่

โค้ดฟังก์ชัน `rerank()` จาก `onlysearchAuthenticRAG.py`:

```python
def rerank(self, query, candidates, top_k=5):
    """Reorder the original retrieval candidates with a cross-encoder."""
    if not candidates:
        return []

    if self.reranker is None:
        raise ValueError("Reranker is disabled; set RAG_USE_RERANKER=1 before starting")

    pairs = [
        (query, source.get("content", ""))
        for _, _, source in candidates
    ]
    scores = np.asarray(
        self.reranker.predict(
            pairs,
            batch_size=16,
            show_progress_bar=False
        )
    ).reshape(-1)

    if len(scores) != len(candidates):
        raise ValueError("Reranker returned an unexpected number of scores")
    if not np.isfinite(scores).all():
        raise ValueError("Reranker returned non-finite scores")

    ranked = [
        (doc_id, float(score), source, rrf_score)
        for (doc_id, rrf_score, source), score
        in zip(candidates, scores)
    ]
    ranked.sort(key=lambda item: (item[1], item[3]), reverse=True)
    return [
        (doc_id, score, source)
        for doc_id, score, source, _ in ranked[:top_k]
    ]
```

อธิบายส่วนสำคัญ:

| โค้ด | หน้าที่และเหตุผล |
|---|---|
| `if not candidates` | คืนรายการว่างเมื่อไม่มีเอกสารให้ประเมิน |
| `if self.reranker is None` | แจ้งข้อผิดพลาดเมื่อเรียก rerank ทั้งที่ยังไม่ได้โหลดโมเดล |
| `(query, source.get("content", ""))` | สร้างคู่คำถามกับเนื้อหาแต่ละ chunk เพื่อให้โมเดลประเมินความเกี่ยวข้องร่วมกัน |
| `self.reranker.predict(...)` | คืนคะแนนหนึ่งค่าต่อคู่คำถาม–ข้อความ |
| `batch_size=16` | ประมวลผลเป็นกลุ่มละไม่เกิน 16 คู่ แทนการเรียกทีละคู่ |
| `np.asarray(...).reshape(-1)` | จัดผลคะแนนให้เป็น array หนึ่งมิติสำหรับจับคู่กับผู้สมัคร |
| ตรวจจำนวนคะแนนและ `np.isfinite()` | ป้องกันจำนวนคะแนนไม่ตรงกับผู้สมัคร หรือมีค่าที่ใช้เรียงไม่ได้ เช่น NaN |
| `zip(candidates, scores)` | จับคะแนนใหม่เข้ากับ chunk เดิม พร้อมเก็บคะแนน RRF ไว้ชั่วคราว |
| `key=lambda item: (item[1], item[3])` | เรียงด้วยคะแนน reranker ก่อน หากคะแนนเท่ากันจึงใช้ RRF ตัดสิน |
| `ranked[:top_k]` | เลือกเอกสารหลังจัดอันดับใหม่ตามจำนวนที่ต้องการ |

ผลที่คืนยังมีรูปแบบ `(doc_id, score, source)` เหมือนเดิม แต่ `score` เปลี่ยนเป็นคะแนนจาก reranker จึงนำไปใช้กับขั้นตอนสร้าง context เดิมได้ โดยไม่ต้องเปลี่ยนเนื้อหาเอกสารใน OpenSearch

> คะแนนจาก reranker ใช้จัดลำดับความเกี่ยวข้อง ไม่ใช่เปอร์เซ็นต์ความถูกต้องของคำตอบ และโมเดลนี้จัดอันดับได้เฉพาะผู้สมัครที่ค้นเจอแล้ว หาก chunk ที่ตอบคำถามไม่อยู่ในรายการผู้สมัคร reranker จะเพิ่ม chunk นั้นเข้ามาเองไม่ได้

#### 2.4.5 หลังปรับ: แทรก Reranking ก่อนเลือก Top-k

โค้ด `hybrid_search()` ของระบบ (2):

```python
def hybrid_search(self, query, k=5, rrf_k=60, use_reranker=None):
    """ค้นหาแบบ hybrid ด้วย RRF ที่รวมผลจาก sparse และ dense search (เหมือนตัวอย่าง)"""
    # ค้นหาด้วย BM25 (sparse)
    sparse_results = self.sparse_search(query, k=k*2)
    print(f"\nSparse search found {len(sparse_results)} results")

    # ค้นหาด้วย vector similarity (dense)
    dense_results = self.dense_search(query, k=k*2)
    print(f"Dense search found {len(dense_results)} results")

    # ใช้ RRF ผสมผลลัพธ์
    rankings = [sparse_results, dense_results]
    fused_results = self.rrf_fusion(rankings, k=rrf_k)
    print(f"RRF fusion returned {len(fused_results)} results")

    # Rerank the SAME fused candidate pool as the bak version.
    # With k=5: BM25 top-10 + dense top-10, up to 20 unique chunks.
    if use_reranker is None:
        use_reranker = self.use_reranker
    if use_reranker:
        return self.rerank(query, fused_results, top_k=k)

    return fused_results[:k]
```

ส่วน BM25, Dense Search และ RRF ใช้วิธีเดิม จุดที่เปลี่ยนคือบรรทัดก่อนคืนผล:

```python
# ระบบ (1): เลือกตาม RRF
return fused_results[:k]

# ระบบ (2): ให้คะแนนผู้สมัครทั้งหมดใหม่ แล้วค่อยเลือก
return self.rerank(query, fused_results, top_k=k)
```

ระบบ (2) ส่ง **ผู้สมัครทั้งหมดหลัง RRF** เข้า reranker ก่อนตัดเหลือ 5 ชิ้น หากตัดเหลือ 5 ก่อน rerank จะเปลี่ยนได้เพียงลำดับของ 5 ชิ้นนั้น และไม่สามารถดึงเอกสารลำดับ 6 เป็นต้นไปขึ้นมาแทนได้

`use_reranker=None` หมายถึงใช้ค่าเริ่มต้นจาก `self.use_reranker` ถ้าปิด reranking จะคืน `fused_results[:k]` แบบเดิม แต่ยังใช้การจัดการ context ของระบบ (2) จึงเหมาะสำหรับเงื่อนไข B ในการทดสอบแยกผลแต่ละส่วน ไม่ใช่ระบบ (1) ที่เหมือนเดิมทุกขั้นตอน

#### 2.4.6 เชื่อมโยงโค้ดกับผลที่ดีขึ้น

ในคำถามเรื่องสาเหตุและการป้องกัน `doc_13` เดิมอยู่ลำดับ 4 หลัง RRF เมื่อส่งคู่ `(คำถาม, เนื้อหาวิธีป้องกัน)` เข้า Cross-Encoder เอกสารนี้ได้รับคะแนนที่ทำให้อยู่ลำดับ 2 หลัง rerank จึงนำข้อมูลการป้องกันไว้ใกล้ต้น context มากขึ้น

ในคำถามเรื่องฉีดวัคซีนแล้วยังติดเชื้อได้หรือไม่ ระบบ (2) เลือก `doc_10` มาอยู่ลำดับ 2 ขณะที่ระบบ (1) ไม่ได้เลือก chunk นี้ใน 5 อันดับแรก แสดงประโยชน์ของการ rerank ผู้สมัครทั้งหมดก่อนเลือก Top-k: ระบบสามารถเปลี่ยนสมาชิกในชุดเอกสารสุดท้ายได้ ไม่ใช่เพียงสลับตำแหน่ง

ข้อแลกเปลี่ยนคือระบบ (2) ต้องประมวลผลโมเดลเพิ่มหลังการค้นหา จึงใช้ทรัพยากรเพิ่มเติม ผลที่มีไม่ได้บันทึกเวลารัน จึงยังระบุไม่ได้ว่าช้าลงเท่าใด และการได้หลักฐานที่เหมาะสมขึ้นยังไม่รับประกันว่าคำตอบจะถูกต้อง เพราะขั้นสร้างคำตอบอาจตีความผิด เสริมข้อมูล หรือชนเพดาน output ได้

## 3. ผลการเปรียบเทียบ: ดีขึ้นอย่างไรและเพราะเหตุใด

### ข้อผิดพลาดที่ต้องแก้ก่อนประเมิน Token Budget

ระบบ (2) บันทึก `prompt_tokens_before_local` และ `prompt_tokens_sent_local` เป็น `2` ทุกข้อ สอดคล้องกับกรณีที่ `apply_chat_template()` คืน dictionary แล้วโค้ดใช้ `len()` นับจำนวนช่องข้อมูล แทนจำนวน token IDs

เอกสาร Transformers ปัจจุบันระบุว่า `return_dict` มีค่าเริ่มต้นเป็น `True` จึงควรกำหนด `return_dict=False` หรืออ่าน `input_ids` ก่อนนับความยาว และตรวจผลกับ `prompt_eval_count` ของ Ollama อีกครั้ง [เอกสาร Transformers](https://huggingface.co/docs/transformers/main_classes/tokenizer)

ดังนั้น **ผลรอบนี้ยังใช้ยืนยันประสิทธิภาพของการจำกัด token ไม่ได้** แม้ API จะสร้างคำตอบสำเร็จทุกข้อ

## 5. ขอบเขตของข้อสรุปและวิธีทดสอบเพิ่มเติม

จากผลที่มี เอกสารอันดับ 1 เหมือนเดิมทั้ง 5 คำถาม ประโยชน์ของ reranking จึงเห็นที่อันดับรองและการเลือกสมาชิกใน 5 อันดับแรก โดยเฉพาะคำถามที่ 2 และ 4

ผลยังไม่เพียงพอที่จะระบุว่าความแม่นยำเพิ่มขึ้นกี่เปอร์เซ็นต์ เพราะไม่มีชุดเอกสารอ้างอิงที่ผู้ตรวจให้ระดับความเกี่ยวข้อง และมีคำถามเพียง 5 ข้อ จึงยังไม่ควรคำนวณ Precision, Recall หรือ nDCG จากคะแนนของระบบเอง

หากต้องการแยกผลของการปรับแต่ละส่วน ควรทดสอบสามเงื่อนไข:

| เงื่อนไข | Reranking | การจัดการ token |
|---|---|---|
| A: ระบบเดิม | ปิด | วิธีเดิม |
| B: ปรับเฉพาะ context | ปิด | วิธีใหม่ที่แก้ตัวนับแล้ว |
| C: ระบบหลังปรับ | เปิด | วิธีใหม่เดียวกับ B |

เปรียบเทียบ A กับ C เพื่อวัดผลรวมของการปรับปรุง และเปรียบเทียบ B กับ C เพื่อแยกผลของ reranking ภายใต้งบ token เดียวกัน

สำหรับการวัดอันดับค้นหา ควรบันทึกผู้สมัครจาก BM25 และ Dense Search ชุดเดียวกัน แล้วเปรียบเทียบอันดับ RRF กับอันดับ reranker โดยให้ผู้ตรวจประเมินความเกี่ยวข้องของ chunks ส่วนการวัดคำตอบควรใช้โมเดล prompt และเพดาน output เดียวกัน พร้อมรันซ้ำเพื่อลดผลจากความแปรผันของการสร้างข้อความ

## 6. ข้อสรุปตามโจทย์

**ระบบ (1) และ (2) ต่างกันที่ระบบ (2) เพิ่ม reranking หลัง Hybrid Search และเพิ่มการจัดการ context ภายใต้งบ token โดยใช้โมเดลสร้างคำตอบตัวเดียวกันในการทดลองรอบนี้**

ผลที่ดีขึ้นชัดเจนคือการจัดเอกสารที่ตรงคำถามให้อยู่ในอันดับสูงขึ้น เช่น เอกสารการป้องกันในคำถามที่ 2 และการเพิ่มหลักฐานเรื่องติดเชื้อซ้ำหลังได้รับวัคซีนในคำถามที่ 4 เหตุผลคือ reranker ประเมินคำถามกับเนื้อหา chunk พร้อมกัน แทนการอาศัยเพียงอันดับจากระบบค้นหาเดิม

อย่างไรก็ตาม คุณภาพคำตอบยังไม่ได้ดีขึ้นทุกข้อ พบทั้งการตอบผิดภาษา การเสริมข้อมูลนอกหลักฐาน และการตัดคำตอบเมื่อชนเพดาน output นอกจากนี้ยังพบข้อผิดพลาดในการนับ token จึงควรแก้ไขและทดสอบเพิ่มเติมก่อนสรุปว่าระบบหลังปรับมีความถูกต้อง ครบถ้วน หรือประหยัดทรัพยากรมากขึ้นโดยรวม
