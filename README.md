# เปรียบเทียบ RAG ก่อนและหลังเพิ่ม Reranking

รายงานนี้ตอบโจทย์ **“อธิบายความแตกต่างระหว่าง (1) และ (2) ว่าต่างกันตรงไหน ดีขึ้นอย่างไร และเพราะเหตุใด”** โดยใช้โค้ดและผล JSON ปัจจุบันในโปรเจกต์

**การปรับหลักในการทดลองนี้คือเพิ่ม reranking โดยไม่ปรับวิธีจัดการ token** วิธีค้นหาเบื้องต้น การตัด context การกำหนด token และโมเดลสร้างคำตอบใช้เหมือนกันทั้งสองระบบ ผลที่เห็นชัดคือเอกสารที่ตอบคำถามบางข้อถูกจัดไว้สูงขึ้น แต่ยังไม่สามารถสรุปว่าคำตอบสุดท้ายดีขึ้นทุกข้อ และตรวจพบความต่างของบรรทัดว่างใน prompt ที่ต้องควบคุมให้ตรงกันในการทดลองครั้งถัดไป

## 1. ระบบและไฟล์ที่นำมาเปรียบเทียบ

| ระบบ | โค้ด | ผลการรัน |
|---|---|---|
| **(1) ก่อนเพิ่ม reranking** | [onlysearchAuthenticRAGbak.py](onlysearchAuthenticRAGbak.py) | [authentic_rag_search_resultsbak.json](authentic_rag_search_resultsbak.json) |
| **(2) หลังเพิ่ม reranking** | [onlysearchAuthenticRAG.py](onlysearchAuthenticRAG.py) | [authentic_rag_search_results.json](authentic_rag_search_results.json) |

ระบบ (2) ใช้ระบบ (1) เป็นฐาน เพิ่ม import `CrossEncoder`, โหลดโมเดล reranker ใน `__init__`, เพิ่มฟังก์ชัน `rerank()` และเรียกฟังก์ชันนี้หลัง RRF ส่วนชื่อไฟล์ผลลัพธ์แยกกันเพื่อไม่เขียนทับผล baseline

จากการเทียบโค้ด เมธอดค้นหา BM25, ค้นหาเวกเตอร์, RRF, ตัด context, เรียก Ollama และรูปแบบ JSON ใช้เหมือนกัน ไม่มี `AutoTokenizer`, token budget แบบใหม่ หรือการปรับงบตาม error 402 ในเวอร์ชันค้นหาปัจจุบัน ส่วน `generate_response()` มีข้อความคำสั่งและค่าพารามิเตอร์เดียวกัน แต่ system prompt (2) มีบรรทัดว่างเพิ่มจากรูปแบบการบันทึกไฟล์ จึงยังไม่เหมือนกันทุกอักขระ

> **ข้อจำกัดในการควบคุมการทดลอง:** ควรทำให้ prompt รวมบรรทัดว่างตรงกัน แล้วรันซ้ำก่อนอ้างว่าความต่างของคำตอบเกิดจาก reranking เพียงอย่างเดียว README นี้รายงานไฟล์และ JSON ที่มีจริง ไม่ได้แก้โค้ดหรือสร้างผลใหม่เพื่อกลบความต่างดังกล่าว

## 2. เหตุผลที่เปลี่ยนไปใช้ Local Model

ในการทดลองก่อนย้ายมา local เคยพบ error 402 จาก OpenRouter เช่น:

```text
Prompt tokens limit exceeded: 9548 > 3793
limit_source: openrouter_credits
```

ข้อจำกัดนี้เกี่ยวข้องกับเครดิตหรืองบคำขอที่รองรับได้ในขณะนั้น **ไม่ใช่ว่า Qwen มี context window สูงสุดเพียง 3,793 tokens** ในประวัติการทดลองพบยอดเครดิตบัญชีติดลบด้วย แม้ key ใหม่จะมีวงเงินรายวันเหลืออยู่ เพราะวงเงินใช้จ่ายของ key ไม่ใช่เครดิตที่เติมให้บัญชี [ข้อจำกัดเครดิตของ OpenRouter](https://openrouter.ai/docs/api_reference/limits)

นอกจากนี้ การประมาณ token ภาษาไทยจากช่องว่างอาจต่ำกว่าความจริง ทำให้ prompt ที่ส่งจริงยาวกว่าที่คาดไว้ เมื่อเครดิตไม่พอจึงสร้างคำตอบไม่สำเร็จ

เพื่อทดสอบซ้ำโดยไม่พึ่งเครดิต OpenRouter จึงเปลี่ยน **ทั้งสองระบบ** มาใช้ `qwen2.5:7b` ผ่าน Ollama ที่ `http://127.0.0.1:11434/api/chat` โดยเลือก 7B ให้เหมาะกับเครื่องทดลอง RAM ประมาณ 16 GB และ RTX 2060 VRAM 6 GB มากกว่ารุ่น 72B รุ่นบีบอัดที่ระบุใน Ollama มีขนาดไฟล์ประมาณ 4.7 GB สำหรับ 7B และ 47 GB สำหรับ 72B [Qwen2.5 7B](https://ollama.com/library/qwen2.5:7b), [Qwen2.5 72B](https://ollama.com/library/qwen2.5:72b)

ค่าที่ส่งเข้า Ollama เหมือนกันทั้งสองโปรแกรม:

```python
"stream": False,

```

## 3. อธิบายความแตกต่างระหว่าง (1) และ (2) ต่างกันตรงไหน ดีขึ้นอย่างไร เพราะเหตุใด

### 3.1 ขั้นตอนของระบบ (1)

```text
คำถาม → BM25 + Dense Search → RRF → เลือก Top-5
      → เตรียมและตัด context → Qwen2.5 7B → คำตอบ
```

BM25 ค้นจากคำที่ตรงกัน ส่วน Dense Search ใช้ `BAAI/bge-m3` แปลงคำถามเป็นเวกเตอร์แล้วค้นด้วย `knn` ใน OpenSearch จากนั้น RRF รวมอันดับของทั้งสองวิธีและเลือก 5 chunks แรก

### 3.2 ขั้นตอนของระบบ (2)

```text
คำถาม → BM25 + Dense Search → RRF → Cross-Encoder Reranker
      → เลือก Top-5 → เตรียมและตัด context → Qwen2.5 7B → คำตอบ
```

Reranker อ่านคำถามกับเนื้อหาแต่ละ chunk พร้อมกันเพื่อให้คะแนนความเกี่ยวข้อง แล้วเรียงผู้สมัครใหม่ก่อนเลือก Top-5

| ประเด็น | (1) ก่อน rerank | (2) หลัง rerank |
|---|---|---|
| เอกสารและ indices | ชุดเดียวกันตามการตั้งค่า | ชุดเดียวกันตามการตั้งค่า |
| Embedding | `BAAI/bge-m3` | `BAAI/bge-m3` |
| ค้นหาเบื้องต้น | BM25 + Dense Search | BM25 + Dense Search |
| จำนวนที่ดึงต่อวิธี เมื่อ `k=5` | 10 chunks | 10 chunks |
| รวมอันดับ | RRF, `rrf_k=60` | RRF, `rrf_k=60` |
| จัดอันดับเพิ่ม | ไม่มี | `BAAI/bge-reranker-v2-m3` |
| จำนวนผลสุดท้าย | 5 chunks | 5 chunks |
| การตัด context | นับส่วนที่คั่นด้วยช่องว่าง × 1.3 | วิธีเดียวกับ (1) |
| ค่า `max_tokens` ของฟังก์ชันตัด context | 4,000 โดยเป็นค่าประมาณ | 4,000 โดยเป็นค่าประมาณ |
| LLM สร้างคำตอบ | Qwen2.5 7B ผ่าน Ollama | Qwen2.5 7B ผ่าน Ollama |
| Context window ที่ตั้ง | 16,384 tokens | 16,384 tokens |
| เพดานคำตอบ | 1,000 tokens | 1,000 tokens |
| Temperature ตอนสร้างคำตอบ | 0.6 | 0.6 |
| Prompt | ข้อความคำสั่งเดิม | ข้อความเดียวกัน แต่มีบรรทัดว่างเพิ่ม |
| คะแนนใน JSON | RRF score | Reranker score |

การทดลองปัจจุบันจึงมุ่งศึกษา **reranking** โดยควบคุมวิธีจัดการ token ให้เหมือนกัน แต่ยังมีข้อจำกัดเรื่องบรรทัดว่างของ prompt ผลต่างของจำนวน token ที่ใช้จริงเกิดได้จากทั้ง chunks ที่ยาวต่างกันและรูปแบบ prompt แม้จำนวน chunks และวิธีตัด context เหมือนกัน

## 4. โค้ดก่อนและหลัง Rerank พร้อมคำอธิบาย

ตัวอย่างต่อไปนี้คัดจากไฟล์ปัจจุบัน เป็นเมธอดในคลาส `AuthenticSearchRAG` ไม่ใช่โปรแกรม standalone

### 4.1 ก่อนปรับ: เลือกตาม RRF

จาก `onlysearchAuthenticRAGbak.py`:

```python
def hybrid_search(self, query, k=5, rrf_k=60):
    """ค้นหาแบบ hybrid ด้วย RRF ที่รวมผลจาก sparse และ dense search (เหมือนตัวอย่าง)"""
    # ค้นหาด้วย BM25 (sparse)
    sparse_results = self.sparse_search(query, k=k*2)
    print(f"\nSparse search found {len(sparse_results)} results")

    # ค้นหาด้วย vector similarity (dense)
    dense_results = self.dense_search(query, k=k*2)
    print(f"Dense search found {len(dense_results)} results")

    # ใช้ RRF ผสมผลลัพธ์
    rankings = [sparse_results, dense_results]
    fused_results = self.rrf_fusion(rankings, k=rrf_k)
    print(f"RRF fusion returned {len(fused_results)} results")

    return fused_results[:k]
```

1. `sparse_search(query, k=k*2)` ค้นหา BM25 จำนวน 10 chunks เมื่อ `k=5`
2. `dense_search(query, k=k*2)` ค้นหาเวกเตอร์จำนวนเท่ากัน
3. `rrf_fusion()` รวมอันดับ โดยรวม chunk ที่มี `doc_id` เดียวกัน
4. `fused_results[:k]` เลือกตาม RRF ทันที จึงไม่มีการประเมินคำถามกับเนื้อหาร่วมกันเพิ่มเติม

### 4.2 RRF ที่ใช้เหมือนกันทั้งสองระบบ

```python
def rrf_fusion(self, rankings, k=60):
    """ผสมผลลัพธ์การค้นหาด้วย Reciprocal Rank Fusion (เหมือนในตัวอย่าง)"""
    fused_scores = {}
    doc_sources = {}

    for ranker_id, results in enumerate(rankings):
        for rank, (doc_id, score, source) in enumerate(results):
            if doc_id not in fused_scores:
                fused_scores[doc_id] = 0
                doc_sources[doc_id] = source

            # RRF formula: 1 / (k + rank)
            fused_scores[doc_id] += 1.0 / (k + rank)

    # เรียงลำดับตาม RRF score
    sorted_results = sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
    return [(doc_id, score, doc_sources[doc_id]) for doc_id, score in sorted_results]
```

ผลค้นหาแต่ละรายการมีรูปแบบ `(doc_id, score, source)` โดย `source` มีเนื้อหา chunk ฟังก์ชันใช้ **อันดับ** คำนวณส่วนร่วม `1 / (k + rank)` แทนการบวกคะแนน BM25 กับ vector โดยตรง เพราะคะแนนสองระบบมีสเกลต่างกัน

โค้ดจริงใช้ `enumerate()` ที่เริ่มอันดับจาก 0 ดังนั้นอันดับแรกมีส่วนร่วม `1/60 ≈ 0.01667` เมื่อ `k=60` หาก chunk ปรากฏทั้งสองรายการจะได้ส่วนร่วมจากทั้งสองรายการ `k` ในสูตร RRF เป็นค่าคงที่ในสูตร ส่วน `k` ใน `hybrid_search()` เป็นจำนวนผลสุดท้าย

### 4.3 หลังปรับ: โหลด Reranker หนึ่งครั้ง

```python
from sentence_transformers import SentenceTransformer, CrossEncoder

# อยู่ใน __init__ ของ AuthenticSearchRAG
self.reranker = CrossEncoder(
    "BAAI/bge-reranker-v2-m3",
    max_length=512,
)
```

Cross-Encoder เป็นโมเดลให้คะแนน ไม่ใช่โมเดลสร้างคำตอบสุดท้าย โหลดครั้งเดียวเพื่อใช้ซ้ำทุกคำถาม ส่วน `max_length=512` จำกัด tokens ของคู่คำถาม–chunk เฉพาะตอนให้คะแนน ข้อความที่ยาวอาจถูกตัดในขั้นนี้ แต่ไม่ได้ตัด `source` ที่เก็บเนื้อหาเต็มสำหรับสร้าง context

### 4.4 หลังปรับ: ให้คะแนนและเรียงใหม่

```python
def rerank(self, query, candidates, top_k=5):
    """Reorder the original retrieval candidates with a cross-encoder."""
    if not candidates:
        return []

    if self.reranker is None:
        raise ValueError("Reranker has not been initialized")

    pairs = [
        (query, source.get("content", ""))
        for _, _, source in candidates
    ]
    scores = np.asarray(
        self.reranker.predict(
            pairs,
            batch_size=16,
            show_progress_bar=False
        )
    ).reshape(-1)

    if len(scores) != len(candidates):
        raise ValueError("Reranker returned an unexpected number of scores")
    if not np.isfinite(scores).all():
        raise ValueError("Reranker returned non-finite scores")

    ranked = [
        (doc_id, float(score), source, rrf_score)
        for (doc_id, rrf_score, source), score
        in zip(candidates, scores)
    ]
    ranked.sort(key=lambda item: (item[1], item[3]), reverse=True)
    return [
        (doc_id, score, source)
        for doc_id, score, source, _ in ranked[:top_k]
    ]
```

| ส่วนของโค้ด | คำอธิบาย |
|---|---|
| `if not candidates` | คืนรายการว่างเมื่อไม่มีผู้สมัคร |
| ตรวจ `self.reranker` | ป้องกันการเรียกให้คะแนนขณะไม่มีโมเดล |
| `(query, source.get("content", ""))` | สร้างคู่คำถามกับข้อความ ให้โมเดลประเมินความสัมพันธ์ร่วมกัน |
| `predict(..., batch_size=16)` | ให้คะแนนคู่ข้อมูลเป็นกลุ่ม ไม่เกิน 16 คู่ต่อ batch |
| `np.asarray(...).reshape(-1)` | จัดคะแนนเป็น array หนึ่งมิติสำหรับจับคู่กับ chunks |
| ตรวจจำนวนคะแนนและ `np.isfinite()` | ป้องกันคะแนนไม่ตรงจำนวนผู้สมัครหรือมีค่าที่เรียงไม่ได้ |
| `zip(candidates, scores)` | จับคะแนนใหม่กับ chunk เดิม และเก็บ RRF score ไว้ชั่วคราว |
| `key=lambda item: (item[1], item[3])` | เรียงด้วย reranker score ก่อน ถ้าเท่ากันใช้ RRF score ตัดสิน |
| `ranked[:top_k]` | เลือก Top-k หลังเรียงใหม่ |

รูปแบบผลยังเป็น `(doc_id, score, source)` จึงใช้กับขั้นสร้าง context เดิมได้ แต่ `score` เปลี่ยนเป็นคะแนน reranker ไม่ใช่เปอร์เซ็นต์ความถูกต้องของคำตอบ

### 4.5 หลังปรับ: แทรกขั้นใหม่ก่อนเลือก Top-k

```python
def hybrid_search(self, query, k=5, rrf_k=60):

    """ค้นหาแบบ hybrid ด้วย RRF ที่รวมผลจาก sparse และ dense search (เหมือนตัวอย่าง)"""

    # ค้นหาด้วย BM25 (sparse)

    sparse_results = self.sparse_search(query, k=k*2)

    print(f"\nSparse search found {len(sparse_results)} results")



    # ค้นหาด้วย vector similarity (dense)

    dense_results = self.dense_search(query, k=k*2)

    print(f"Dense search found {len(dense_results)} results")



    # ใช้ RRF ผสมผลลัพธ์

    rankings = [sparse_results, dense_results]

    fused_results = self.rrf_fusion(rankings, k=rrf_k)

    print(f"RRF fusion returned {len(fused_results)} results")



    # ให้คะแนนผู้สมัครชุดเดิมทั้งหมดก่อนเลือก Top-k
    return self.rerank(query, fused_results, top_k=k)
```

จุดเปลี่ยนหลักคือ:

```python
# ก่อน
return fused_results[:k]

# หลัง
return self.rerank(query, fused_results, top_k=k)
```

เมื่อ `k=5` ระบบนำผู้สมัครหลัง RRF ซึ่งมีได้สูงสุด 20 chunks ที่ไม่ซ้ำเข้า reranker **ก่อน** ตัดเหลือ 5 ทำให้เอกสารนอก Top-5 เดิมขึ้นมาแทนได้ หากตัด 5 ชิ้นก่อน rerank จะเปลี่ยนได้เพียงลำดับภายในชุดนั้น และ reranker ไม่สามารถเพิ่มเอกสารที่ไม่อยู่ในผู้สมัครเองได้

### 4.6 โค้ดการตัด Context ที่คงเหมือนกัน

```python
def truncate_context(self, context, max_tokens=4000):
    """ย่อ context ให้มีขนาดไม่เกิน max_tokens"""
    words = context.split()
    estimated_tokens = len(words) * 1.3

    if estimated_tokens <= max_tokens:
        return context

    target_words = int(max_tokens / 1.3)
    truncated_context = " ".join(words[:target_words])
    return truncated_context + " ...(truncated)"
```

วิธีนี้ยังมีข้อจำกัดสำหรับภาษาไทย เพราะจำนวนส่วนจาก `split()` ไม่เท่ากับจำนวน tokens ของโมเดล จึงไม่ได้รับประกันว่า context ไม่เกิน 4,000 tokens จริง แต่เก็บไว้เหมือนกันทั้งสองฝั่งเพื่อแยกผลของ reranking การทดลองนี้ไม่ได้เพิ่ม tokenizer หรือปรับ token budget ฝั่งใดฝั่งหนึ่ง

## 5. ผลทดลองจาก JSON ปัจจุบัน

ทั้งสองไฟล์มีคำถามเดียวกัน 5 ข้อ และมีเพียง `question`, `answer`, `results` สอดคล้องกับรูปแบบผลลัพธ์ของโค้ดปัจจุบัน การวิเคราะห์ต่อไปนี้ใช้ผลที่มีอยู่ ไม่ได้สร้างผลรันใหม่ระหว่างเขียน README

### 5.1 การเปลี่ยนอันดับและชุดเอกสาร

| คำถาม | (1) ก่อน rerank | (2) หลัง rerank | เอกสารร่วมกัน |
|---|---|---|---|
| 1 | doc_1 → doc_2 → doc_3 → doc_7 → doc_6 | doc_1 → doc_2 → doc_6 → doc_3 → doc_7 | 5/5 |
| 2 | doc_2 → doc_0 → doc_1 → doc_13 → doc_15 | doc_2 → doc_13 → doc_1 → doc_10 → doc_3 | 3/5 |
| 3 | doc_6 → doc_1 → doc_2 → doc_11 → doc_13 | doc_6 → doc_1 → doc_10 → doc_9 → doc_13 | 3/5 |
| 4 | doc_13 → doc_2 → doc_11 → doc_1 → doc_3 | doc_13 → doc_10 → doc_11 → doc_2 → doc_6 | 3/5 |
| 5 | doc_1 → doc_2 → doc_6 → doc_3 → doc_10 | doc_1 → doc_2 → doc_6 → doc_10 → doc_3 | 5/5 |

- เอกสารอันดับ 1 เหมือนกัน **5/5 คำถาม** ประโยชน์ที่เห็นจึงอยู่ในอันดับรองและสมาชิกของ Top-5
- ข้อ 1 และ 5 ใช้เอกสารชุดเดิมแล้วสลับอันดับ
- ข้อ 2, 3 และ 4 เปลี่ยนสมาชิกบางส่วน โดยมีเอกสารร่วมกัน 3 จาก 5 ชิ้น
- จำนวนเอกสารร่วมกันไม่ได้บอกความแม่นยำ ต้องอ่านความเกี่ยวข้องกับคำถามเพิ่มเติม

### 5.2 คำถามที่ 1: หัดและหัดเยอรมันแตกต่างกันอย่างไร?

**ผลค้นหา:** `doc_6` เรื่องภาวะแทรกซ้อนในหญิงตั้งครรภ์ขึ้นจากลำดับ 5 เป็น 3 แต่ใช้เอกสาร 5 ชิ้นชุดเดิม

**คำตอบ:** ก่อนปรับระบุสาเหตุของหัดเป็น `Parvovirus B19` หลังปรับระบุเป็น `Coxsackievirus` ซึ่งผิดทั้งสองแบบ โดย CDC ระบุว่าไวรัสหัดอยู่ในสกุล **Morbillivirus** [ข้อมูล CDC](https://www.cdc.gov/measles/hcp/clinical-overview/index.html)

**ประเมิน:** ยังไม่มีหลักฐานว่าคำตอบถูกต้องขึ้นในข้อนี้ แม้ลำดับเอกสารเปลี่ยนแล้ว และเอกสารที่เลือกทั้งหมดเน้นหัดเยอรมัน จึงควรตรวจว่าค้นข้อมูลฝั่งโรคหัดได้เพียงพอหรือไม่

### 5.3 คำถามที่ 2: สาเหตุและการป้องกันโรคหัดเยอรมัน

**ผลค้นหา:** `doc_13` เรื่องการป้องกันขึ้นจากลำดับ **4 เป็น 2** พร้อมแทนหัวเรื่อง `doc_0` และเอกสารอ้างอิง `doc_15` ด้วยคำแนะนำ `doc_10` และอาการ `doc_3`

```text
ก่อน: สาเหตุ → หัวเรื่อง → ภาพรวม → การป้องกัน → เอกสารอ้างอิง
หลัง: สาเหตุ → การป้องกัน → ภาพรวม → คำแนะนำ → อาการ
```

**ดีขึ้นอย่างไร:** สองลำดับแรกตรงกับสองส่วนของคำถาม และลด chunks ที่มีเพียงหัวเรื่องหรือรายการอ้างอิง คำตอบหลังปรับแบ่งหัวข้อสาเหตุ กลุ่มผู้รับวัคซีน และแนวทางช่วงระบาดชัดเจนขึ้น รวมถึงระบุรายละเอียดที่ก่อนปรับกล่าวไม่ครบ เช่น ช่วงคุมกำเนิดตามข้อความต้นทาง

**ข้อจำกัด:** ทั้งสองมีคำตอบที่จบข้อความใน JSON รอบนี้ แต่ไม่มี `finish_reason` จึงไม่ยืนยันเหตุผลที่จบ คำตอบหลังปรับยังมีถ้อยคำเรื่องหญิงที่ตั้งครรภ์กับการฉีดวัคซีนที่อาจทำให้เข้าใจผิด การสอดคล้องกับ corpus ไม่ใช่การรับรองว่าเป็นคำแนะนำทางการแพทย์ที่ถูกต้องทั้งหมด

### 5.4 คำถามที่ 3: ทำไมหัดเยอรมันอันตรายต่อหญิงตั้งครรภ์?

**ผลค้นหา:** `doc_6` ยังเป็นอันดับ 1 ทั้งสองระบบ หลังปรับเพิ่มคำแนะนำ `doc_10` และการรักษา `doc_9` แทนสาเหตุ `doc_2` และข้อบ่งชี้ไปพบแพทย์ `doc_11`

**คำตอบ:** หลังปรับจัดหมวดการแพร่เชื้อ ภาวะแทรกซ้อน และอาการทารกละเอียดขึ้น แต่มีข้อผิดพลาดใหม่คือเขียน **“ต้อกระจก (Microphthalmia)”** ขณะที่ `doc_6` ใช้ `Microphthalmia` กับ **นัยน์ตาเล็ก** นอกจากนี้ ทั้งสองขยายการใช้ตัวเลข 60–85% จากช่วงเดือนที่ 2 ในต้นทางไปเป็นช่วงที่กว้างกว่า

**ประเมิน:** ได้เอกสารรองเกี่ยวกับการดูแลเพิ่ม แต่ยังสรุปไม่ได้ว่าคำตอบดีขึ้นโดยรวม รายละเอียดมากขึ้นพร้อมความผิดพลาดมากขึ้นได้เช่นกัน

### 5.5 คำถามที่ 4: ฉีดวัคซีนแล้ว ยังติดเชื้อได้หรือไม่?

**ผลค้นหา:** ทั้งสองได้ `doc_13` เป็นอันดับ 1 หลังปรับเพิ่ม `doc_10` มาเป็นอันดับ **2** เอกสารนี้มีข้อความว่าผู้ได้รับวัคซีนยังอาจติดเชื้อซ้ำได้ ขณะที่ระบบ (1) ไม่ได้เลือก chunk นี้ใน Top-5

**ดีขึ้นอย่างไร:** ชุดหลักฐานมีข้อความตอบประเด็นโดยตรงเพิ่ม ไม่ได้อาศัยเฉพาะคำอธิบายเรื่องวิธีป้องกัน

**คำตอบและข้อจำกัด:** ทั้งก่อนและหลังตอบว่าความเสี่ยงต่ำแต่ไม่เป็นศูนย์ หลังปรับเพิ่มตัวเลข **95–97% สำหรับวัคซีนสองเข็ม** ซึ่งไม่พบตัวเลขชุดนี้ใน chunks ที่เลือก จึงยังมีข้อมูลนอกหลักฐาน อีกทั้งมีข้อความซ้ำ “100% 100%” และคำว่า “การติดเชื้อแบบผู้นำ” ที่ไม่ชัดเจน

**ประเมิน:** การเลือกหลักฐานดีขึ้น แต่คำตอบสุดท้ายยังไม่ดีขึ้นทุกด้าน

### 5.6 คำถามที่ 5: ผลต่อสาธารณสุขและเศรษฐกิจของประเทศ

**ผลค้นหา:** ใช้เอกสารชุดเดียวกัน หลังปรับเลื่อนคำแนะนำ `doc_10` จากลำดับ 5 เป็น 4 และเลื่อนอาการ `doc_3` ลงหนึ่งอันดับ

**คำตอบ:** ก่อนปรับกล่าวถึงระบบสาธารณสุข วัคซีน งบประมาณ การลงทุน และการศึกษา หลังปรับจัดกลุ่มเป็นสาธารณสุข เศรษฐกิจ การท่องเที่ยว การผลิต และการบริหารจัดการ โดยมีความยาวลดจาก 1,786 เป็น 1,541 อักขระ

**ประเมิน:** คำตอบสั้นลง แต่ไม่ได้พิสูจน์ว่าถูกต้องขึ้น เพราะ chunks ที่เลือกไม่มีหลักฐานเศรษฐกิจระดับประเทศโดยตรง และหลังปรับยังมีถ้อยคำเช่น “การลี้ภัยจากผู้ที่ต้องการท่องเที่ยว” ที่ไม่ชัดเจน ข้อนี้ยังต้องเพิ่มหรือค้นหลักฐานให้ตรงประเด็น

## 6. เพราะเหตุใด Reranking จึงช่วยได้

BM25 ช่วยค้นจากคำที่ตรงกัน Dense Search ช่วยค้นจากความใกล้เคียงของ embedding และ RRF รวมอันดับ แต่ข้อความที่กล่าวถึงหัวข้อเดียวกันไม่ได้ตอบคำถามทุกแบบได้ดีเท่ากัน

Cross-Encoder ประเมินคู่คำถาม–ข้อความโดยตรง จึงสามารถเลื่อนเอกสารที่ตอบส่วนสำคัญขึ้นหรือเลือกเอกสารนอก Top-5 เดิมมาแทนได้ ข้อ 2 แสดงการเลื่อนเอกสารการป้องกันขึ้น และข้อ 4 แสดงการเพิ่มข้อความเกี่ยวกับการติดเชื้อซ้ำหลังวัคซีน

ข้อแลกเปลี่ยนคือมีขั้นประมวลผลเพิ่มเติมและใช้ RAM/VRAM มากขึ้น รวมถึง `max_length=512` อาจทำให้ reranker ไม่เห็นเนื้อหาท้าย chunk ยาว ไม่มีข้อมูลเวลาใน JSON จึงยังระบุไม่ได้ว่าช้าลงเท่าใด

Reranker จัดอันดับผู้สมัครที่ค้นเจอแล้ว ไม่ได้แก้ข้อมูลใน corpus สร้างหลักฐานที่ไม่มี หรือบังคับให้ LLM ตีความถูกต้อง ดังนั้นควรแยกการประเมิน **ความเหมาะสมของหลักฐาน** ออกจาก **ความถูกต้องของคำตอบ**

## 7. ข้อจำกัดด้าน Token และข้อมูลผลทดลอง

JSON รอบนี้ทั้งสองไฟล์มีเพียง `question`, `answer`, `results` ไม่มี `generation`, token usage, finish reason หรือเวลารัน แม้ `call_qwen_api()` เก็บ usage ไว้ใน `self.last_generation` และแสดงบนหน้าจอ แต่ `search_for_question()` ไม่ได้ส่งข้อมูลนี้ไปบันทึก JSON

จึงสรุปได้เพียงว่ามีข้อความคำตอบครบ **5 จาก 5 คำขอ** ทั้งสองฝั่งและไม่พบข้อความ error ในไฟล์ ไม่สามารถคำนวณการประหยัด token เปรียบเทียบความเร็ว หรือยืนยันว่าแต่ละคำตอบหยุดเพราะเหตุใดได้ ไม่ควรนำตัวเลข token ของ JSON เวอร์ชันก่อนมาใช้กับรอบนี้

| คำถาม | ความยาวคำตอบ (1) | ความยาวคำตอบ (2) |
|---|---:|---:|
| 1 | 1,320 | 1,271 |
| 2 | 1,491 | 1,514 |
| 3 | 1,097 | 1,419 |
| 4 | 648 | 729 |
| 5 | 1,786 | 1,541 |

ตัวเลขในตารางเป็น **จำนวนอักขระ ไม่ใช่ tokens** และไม่ได้เป็นคะแนนคุณภาพ คำตอบที่ยาวขึ้นหรือสั้นลงอาจยังมีข้อผิดพลาดได้

ช่อง `context` ของ chunks ทั้งสองชุดเป็นข้อความว่าง จึงไม่มีบริบทเสริมในผลที่ส่งออก แต่ไม่สามารถสรุปจากช่องนี้อย่างเดียวว่า embedding ตอนนำเข้าไม่เคยใช้บริบทเสริม

คะแนน RRF ประมาณ `0.016` กับ reranker ใกล้ `0.98` เป็นคะแนนคนละชนิด จึงไม่สามารถอ้างว่าความแม่นยำเพิ่มขึ้นเป็น 98% ได้

ไม่ต้องนำเข้าข้อมูลใหม่เพียงเพราะเปลี่ยนโมเดลตอบคำถาม หาก index เดิมพร้อมใช้ การรันไฟล์นำเข้าใหม่ยังเรียก OpenRouter ตามโค้ด `authenticRAG*.py` ปัจจุบัน

### วิธีทำให้ข้อสรุปแข็งแรงขึ้น

1. ใช้คำถาม corpus index โมเดล วิธีตัด context และเพดาน output เดียวกัน และแก้ prompt รวมบรรทัดว่างให้ตรงกันทุกอักขระก่อนรันครั้งถัดไป
2. บันทึกผู้สมัครจาก BM25 และ Dense Search ชุดเดียวกัน แล้วเทียบอันดับ RRF กับ reranker เพื่อควบคุมความแปรผันของขั้นค้นหา
3. ให้ผู้ตรวจประเมินความเกี่ยวข้องของ chunks เช่น 0 ไม่เกี่ยวข้อง, 1 เกี่ยวข้องบางส่วน, 2 ตอบคำถามโดยตรง แล้ววัด nDCG@5 หรือ MRR@5 หากวัด Recall ต้องมีชุดอ้างอิงของ chunks ที่เกี่ยวข้องด้วย
4. ประเมินคำตอบแยกตามความถูกต้อง ความครบถ้วน ความชัดเจน และความสอดคล้องกับหลักฐาน โดยไม่ใช้คะแนนค้นหาหรือความยาวคำตอบแทน
5. รันซ้ำหลายรอบและเพิ่มคำถาม เพราะ `temperature=0.6` และไม่ได้กำหนด seed คำตอบจึงมีความแปรผันได้
6. หากต้องวัด token และเวลา ให้เพิ่มการบันทึกแบบเดียวกันทั้งสองฝั่งในการทดลองรอบถัดไป โดยไม่ปรับวิธีจัดการ context ฝั่งเดียว

ผลปัจจุบันมีเพียง 5 คำถาม ไม่มี relevance labels และไม่มีการรันซ้ำที่บันทึกไว้ จึงยังไม่ควรสรุปเป็นเปอร์เซ็นต์ความแม่นยำที่ดีขึ้น หรืออ้างว่าดีขึ้นกับทุกคำถาม

## 9. ข้อสรุปตามโจทย์

**ต่างกันตรงไหน:** (1) เลือก Top-5 จาก RRF โดยตรง ส่วน (2) เพิ่ม Cross-Encoder จัดอันดับผู้สมัครหลัง RRF ก่อนเลือก Top-5 ส่วน embedding การค้นหา การตัด context และ LLM สร้างคำตอบเหมือนกัน แต่ตรวจพบบรรทัดว่างใน prompt ต่างกันเล็กน้อย จึงต้องควบคุมจุดนี้ก่อนสรุปผลของคำตอบแบบแยกสาเหตุ

**ดีขึ้นอย่างไร:** หลักฐานที่ตรงคำถามขึ้นมาอยู่สูงขึ้นในข้อ 2 และเพิ่มหลักฐานเรื่องติดเชื้อหลังวัคซีนในข้อ 4 การปรับนี้ช่วยคุณภาพการเลือก context แต่คำตอบไม่ได้ดีขึ้นทุกด้าน ยังพบข้อเท็จจริงผิด ข้อมูลนอกหลักฐาน และถ้อยคำไม่ชัด

**เพราะเหตุใด:** Reranker ประเมินความสัมพันธ์ระหว่างคำถามกับข้อความเพิ่มเติมจากอันดับ BM25 และ Dense Search จึงเปลี่ยนได้ทั้งลำดับและสมาชิกในชุดเอกสารสุดท้าย อย่างไรก็ตาม ไม่ได้รับประกันว่า LLM จะใช้หลักฐานนั้นได้ถูกต้องเสมอ

**การย้ายไป local:** ช่วยให้ทดลองโดยไม่พึ่งเครดิต OpenRouter และใช้ 7B ตัวเดียวกันทั้งสองฝั่ง แต่เป็นการเตรียมสภาพแวดล้อม ไม่ใช่ประโยชน์ที่เกิดจาก reranking และยังมีข้อจำกัดด้าน context window หน่วยความจำ และเพดานคำตอบ
